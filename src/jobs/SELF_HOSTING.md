# Scheduled Tasks

New exports include Jobs configuration only when the project has the `jobs` plan feature (included in paid plans). An existing export has no ongoing WeWeb license check. Use independent storage for independent operation: sharing a hosted Jobs database also shares its execution pause switch.

The exported Node server runs the Jobs loop alongside HTTP. Run one exported environment per process, with Node 24.11 or later, `ENV=production` (or `staging` / `editor`) and `WEWEB_JOBS_SELF_HOSTED=true`. Start the built export with `node index.mjs`. Tasks run in the main process and share its loaded integrations. No separate worker entry or heartbeat process is needed. Cancellation and task timeouts are cooperative: the engine checks between actions, loop iterations, nested workflows and stream chunks. The Wait action supports cancellation; custom JavaScript can pass `context.signal` to compatible APIs. Arbitrary synchronous code cannot be interrupted per task and blocks HTTP and other tasks in that process. Await all asynchronous work inside your actions; detached promises and timers are not managed task executions.

Use the environment's exported Jobs configuration. WeWeb Table uses `DATABASE_URL`; the server automatically installs and upgrades its managed schema on startup. PostgreSQL must allow schema, table and function changes. With Supabase, supply the connection's server secret through the exported environment variables. Either provide `JOBS_DATABASE_URL` with direct PostgreSQL access for automatic upgrades, or apply the new export's `jobs-production.sql` (matching your selected environment) in the Supabase SQL editor before starting the new server. The managed public RPC functions permit `service_role`, and deny `anon` / `authenticated` / PUBLIC.

Upgrades apply only missing numbered migrations and preserve existing jobs and history. With direct SQL access, the new process asks the old worker to stop claiming, waits for it to finish its attempts and release ownership by retrying initialization, and then applies the upgrade atomically. Old processes refuse to run against an incompatible schema. Stop and replace all old replicas; do not leave them restarting indefinitely. Without direct SQL access, stop all old replicas gracefully before applying the exported SQL. The SQL refuses to upgrade while the installed schema reports active ownership. Self-hosted ownership never expires: after a crash, follow the recovery procedure below before retrying the upgrade. Never delete Jobs tables or change installation IDs to upgrade.

A failed migration rolls back its schema changes and version history together. Correct the failure and restart with the same export (or rerun its SQL). The upgrade barrier remains until the migration succeeds. Once an upgrade commits, rolling back to an export requiring an older schema is rejected; deploy a compatible export instead. Do not manually edit the managed tables, functions or migration history. The operator recovery procedure below uses the existing owner-release RPC.

Managed tables use the fixed `jobs` schema and the `public.jobs_*` RPC functions. Use separate databases when environments should have separate Jobs storage. All replicas must use the same installation and database. The database grants one worker lease per environment; that worker runs up to the configured number of parallel jobs. Handle SIGTERM gracefully and allow time for running attempts to stop. The self-hosted owner does not expire automatically. A crash, a stuck task or an ungraceful stop requires operator intervention; there is no watchdog or automatic process restart. Full workflow retries may repeat external effects: use stable operation identifiers with external services that support idempotency.

## Recovering after a crash or blocked process

1. Stop **all replicas connected to this Jobs storage**, confirming the old process is dead. An expired task timeout or a disconnected database is not proof of termination.
2. In that database (or the Supabase SQL editor), release the retained self-hosted owner:

```sql
SELECT public.jobs_release_worker(p_worker_id => worker_id)
FROM jobs.installation
WHERE worker_id IS NOT NULL AND worker_expires_at = 'infinity'::timestamptz;
```

3. Start the replacement server. It recovers abandoned attempts under the normal retry policy, preserving pending work, inputs and history. Cancel-requested attempts remain cancelled. A task already at its retry limit stays failed. If the process stopped during an upgrade, start the intended new export so it can finish its migration first.

Never release a live owner's lock: doing so can execute the same task twice. If the process remains blocked, its HTTP server and other tasks may also be unavailable; stopping and restarting it is the operator's responsibility.

Scheduled timestamps are UTC instants. Cron timezones use IANA names, defaulting to UTC. Missing clock times during daylight saving changes are skipped; repeated times run once. Disabled cron intervals are excluded from backfill. A plan-access pause retains enabled cron definitions; catch-up on restoration follows the configured backfill window. Successful and failed history remains until an explicit cleanup action or cleanup from the editor; cleanup never removes pending work or cron progress.

Redeploy the export to update packaged workflows and schedules. A running process uses its packaged revision; restart all old replicas during a self-hosted update. Do not copy production Jobs tables from another environment or change installation IDs to upgrade an existing installation.

Hosted WeWeb uses an IAM-authenticated Jobs proxy to create EventBridge Scheduler wakeups and invoke the existing project Lambda’s environment alias. HTTP and Tasks share its configured concurrency and timeout; a database lease permits one worker per environment. The proxy derives project ownership from the AWS caller identity and constructs its worker target; customer Lambdas have no direct Scheduler or worker-invocation permissions. The regional proxy URL is injected as `JOBS_LAMBDA_URL` during publication. Scheduling and wakeup operations make no calls to weweb-back. During deployment, the Jobs database stops the old Lambda from claiming work while its active attempts finish. The next invocation uses the new packaged workflows. Staging and Production do not fetch workflow definitions or scheduler state from the WeWeb backend. A hosted owner is protected until the invocation deadline plus a ten-second margin, independently of task timeouts. Before the first task or failure hook executes, the owner registers a one-time wake after its committed SQL lease expires. Empty and duplicate invocations do not register recovery wakes, so there is no periodic recovery tick. A crash can delay recovery until the full invocation deadline; cancellation never releases ownership while user code is still running. If persistence succeeds but a wake signal is lost, the next ordinary wake resumes eligible work. EventBridge has [60-second invocation precision](https://docs.aws.amazon.com/scheduler/latest/UserGuide/schedule-types.html); database eligibility prevents early execution. Lambda [asynchronous retries](https://docs.aws.amazon.com/lambda/latest/dg/invocation-async-error-handling.html) supplement, but do not replace, persisted job retries.
